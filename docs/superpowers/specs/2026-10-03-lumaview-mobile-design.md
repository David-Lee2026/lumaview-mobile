# LumaView Mobile 手机版工程规格

**文档版本：0.1｜日期：2026-10-03｜状态：待书面确认**

**项目范围已确认；本文件是进入实施前的工程设计，不是 APK、已完成源码或真机测试报告。** 文中的算法参数、耗时与掉帧阈值均为设计起点或验收目标，不是测量结果。

## 1. 已确认的目标与交付边界

开发一款本地视频播放器，交互接近常见手机播放器，继承 LumaView Windows 1.1 的播放控制、弱光增强、区域放大、旋转、音量与可视化剪辑能力。优先适配用户指定的 Mate 20 X／HarmonyOS 4.0，以及符合最低条件的 Android ARM64 手机。

首版的核心不是“能装上一个播放器”，而是以下三个流程完整可用：

1. 打开微光或弱光视频，实际改变视频像素而非只调屏幕背光，能在同一时刻对比原画。
2. 用手指框出区域，调整选框并放大播放；增强主要依据当前可视选区，而非仍然只依据全片平均亮度。
3. 在可拖动时间轴上选择 A／B，预览边界并导出原码流片段或精确重编码片段。

**首版必需功能**：本地文件与文件夹授权打开、文件列表、最近播放与断点续播、播放／暂停、快退 10 秒／快进 30 秒、进度条、0.25–2 倍速、音量与静音、屏幕亮度、屏幕方向锁定、视频直角旋转、字幕／音轨选择、区域选择与缩放平移、增强档位与手调、A／B 剪辑与循环预览、截图、故障诊断、明确的性能降级提示。

**不纳入首版完成声明**：HarmonyOS 5／6 原生 HAP；卓易通等兼容环境的全面保证；神经网络超分辨率；运动补偿多帧降噪；增强画面或放大局部的视频转码导出；任意角度旋转；DRM 受保护视频编辑；投屏、在线媒体聚合、云端处理。系统支持时可保留上游画中画／后台音频入口，但它们不替代上述三个核心流程，未验证时明确关闭相应入口。

兼容环境中的 APK 与鸿蒙原生应用不能混称。华为说明 HarmonyOS 5 及以上部分 APK 安装依赖卓易通的实际支持范围。[1] 本规格不以机型名称推定底层 Android API、图形扩展或解码器能力。

### 2.1 固定基线

基于 mpv-android 做源码级二次开发，应用显示名称为 **LumaView Mobile 光影增强播放器**；采用独立应用标识 `org.lumaview.mobile`，不覆盖上游播放器。MX 仅作为交互参考，不使用其商标或闭源代码。

mpv-android 不是可直接导入的 AAR，其原生部分需要独立构建。[5] 保留上游原生构建流程，使用原生 Linux 构建环境；不把 Windows 桌面版 EXE／DLL 复制进 APK。

### 2.2 设备探测与签名

启动诊断读取实际 API、ABI、GPU／GLES 版本、可用解码器、当前解码方式、颜色信息、Surface 尺寸及可用性能计数器。只在设备本地保存，用户主动导出后才分享。不收集设备唯一标识，不自动上传日志或视频。

ARM64 依赖同时检查 4 KB／16 KB 页兼容性。原生库需要实际 ELF 与 APK 对齐检查及可用环境运行验证，不能仅凭使用较新 NDK 就判定通过。[6]

首个可安装版本标为 `0.1.0-test`，可采用测试签名；签名证书摘要随 APK 提供。测试签名、开发签名与正式发布签名明确区分。私钥不写入公开源码或普通日志；以后换签名可能影响覆盖安装，必须在说明中交代。当前没有生成手机端签名或 APK。

## 3. 总体架构与唯一状态来源

| 模块 | 职责 | 必须输出的状态 |
|---|---|---|
| `PlayerSession` | libmpv 生命周期、播放与轨道控制、Surface 协调 | 媒体代次、位置、时长、实际暂停状态、视频参数、解码方式 |
| `GestureRouter` | 触点归属、按钮／滑块／框选／平移优先级 | 活跃手势、指针 ID、取消／提交事件 |
| `ViewportController` | 源坐标、容器裁剪、旋转、显示比例、缩放平移 | 屏幕映射矩阵、当前可视源区域、变换代次 |
| `EnhancementController` | 档位、手调、锁定、原画对比、性能决策 | 请求参数、实际生效档位、降级／旁路原因 |
| `NativeEnhancementStage` | GPU 区域统计、平滑参数、空间降噪、提亮与高光保护 | 参数应用回执、输入颜色条件、GPU 资源状态 |
| `ClipController` | A／B、边界预览、循环范围、导出确认 | 请求区间、实际导出区间、模式、所选轨道 |
| `MediaExport` | FFmpeg 原生封装复制；Transformer 精确输出 | 任务 ID、进度、编码方式、完成／取消／失败 |
| `DocumentAccess` | SAF 授权、FD 生命周期、可寻址检查、缓存与新文件提交 | 授权状态、输入句柄、空间检查、输出 URI |

上表是拟新增或改造的模块约定，不代表上游已有这些接口。

播放位置、暂停与速度由内核回报；界面不自行假定设置已经生效。每个异步操作携带 `mediaGeneration` 与递增的 `requestId`，切换媒体、Surface 重建或关闭后，丢弃旧回调。

UI 线程不解码、不转码、不遍历整个视频、不等待 GPU 同步回读。播放命令、文件 I/O 与导出各在受控工作线程执行。导出最多一个任务；开始精确转码时默认暂停预览，避免与播放竞争有限硬件编解码器。

## 4. GPU 路径：框选与增强必须使用同一个区域

### 4.1 主路径

正常增强路径为：

**授权视频 → libmpv 解复用与解码 → 导入解码纹理 → 统一源坐标与颜色状态 → 当前可视区域 GPU 取样 → 区域统计／空间降噪／局部提亮 → 按播放区域缩放 → 字幕与控制层 → 屏幕。**

首选 `vo=gpu`、Android EGL、MediaCodec 硬件解码；只有失败才进入可诊断的复制回读或软件解码路径。直接输出模式 `mediacodec_embed` 不作为本产品“增强已开启”的路径。mpv 文档区分这些路径；还明确了 `video-crop` 的源矩形语义。[7]

**不能只设置 `video-crop` 就宣称“按选区增强”。** 裁剪的显示范围与着色器统计的纹理范围可能不同。统一模块负责把当前可视区域传入统计与增强阶段，放大与统计共享变换代次。若采用显式 ROI 纹理，后续不得再次施加同一裁剪，避免二次裁剪。

无框选时，统计区域为有效视频内容，不含播放器黑边；有框选或双指缩放后，统计区域为屏幕上实际可见的源区域。裁剪外最多加入 5% 尺寸的有限边界上下文，权重不超过 10%；远处亮物不得主导局部曝光。

**区域放大不减少源视频解码分辨率。** 对 4K 文件框出一小块，仍需解码相应视频帧。可减少的是后续增强面积或处理分辨率，不能声称只解码那一小块。

### 4.2 本次核对发现的接口限制

上游 `glsl-shader-opts` 的可调参数接口在文档中限定为 `vo=gpu-next`。[7] 因此，首选的 `vo=gpu` 不能直接照搬该接口。

本设计在受控的 libmpv GPU 补丁中增加局部增强阶段，通过 JNI 提交一份不可变参数快照，再在渲染线程更新 uniforms／统计资源。具体 C 函数命名在实施计划中确定；它不是虚构的现成 mpv API。切换档位预编译固定变体，拖动选区或播放逐帧过程中不反复重写着色器文件、重编译 shader 或重开解码器。`gpu-next` 只作为单独验证的候选后端，不作为规避主路径问题的静默替换。

### 4.3 颜色、裁剪与生命周期

SDR 增强明确输入的色彩矩阵、传递函数与全／有限范围；曝光变换以线性光工作值计算，统计可使用规范化亮度编码，输出回到管线声明的工作空间。不得把已完成 YUV／RGB 变换的数据重复扩展范围。用灰阶与肤色测试块验证黑白电平、色相和伽马。

容器固有裁剪、像素宽高比、文件旋转信息与用户附加旋转只合成一次。手指屏幕坐标通过逆矩阵映射到源视频有效矩形。取消框选恢复先前视图，恢复全画面保留容器正常显示含义，不擅自显露本应隐藏的编码边缘。

切换文件、跳转、裁剪提交、旋转和 Surface 重建清空增强历史；原画对比不清空视图。Surface 销毁后必须先停止对其提交帧，再释放相关句柄。上游 `BaseMPVView` 已有 Surface 创建／尺寸变化／销毁衔接，但其代码对潜在竞态作了提醒，不能将其原样继承当作已解决。[8]

## 5. 增强算法与交互参数

### 5.1 档位与默认值

| 档位 | 设计含义 | 自动曝光上限起点 | 空间处理 |
|---|---|---:|---|
| 原画 | 关闭本应用像素增强，保留正常颜色显示及当前选区 | 0 EV | 关闭 |
| 自动均衡 | 默认；只对偏暗画面适度处理 | +2 EV | 弱保边降噪 |
| 弱光增强 | 更强的暗部提升和噪声抑制 | +3 EV | 3×3 邻域保边降噪 |
| 极弱光增强 | 增益有上限，高光与颜色保护优先 | +4 EV | 较强降噪，但不默认增加邻域尺寸 |
| 流畅优先 | 保留区域自适应提亮，降低处理成本 | +2 EV | 跳过高成本邻域处理 |

这些数值是初始配置，不是最佳效果结论。正式定值需附同素材、同位置对照结果；调整时保留参数记录。全黑或接近量化底噪的区域提示“有效细节不足”，不生成虚构细节。

手动面板提供曝光偏移 −1 至 +1 EV、暗部／局部提亮强度 0–100、对比度 −25 至 +25、饱和度 0–150、降噪 0–100、细节 0–30，以及单项／全部重置。手动叠加后总曝光仍限制在 0 至 +4 EV；降噪或细节处理不可用时，控件显示原因。

手机背光单独控制：左侧手势只设置当前窗口亮度，不修改系统全局亮度；它不等同于视频曝光。音量条与右侧手势修改同一媒体音量，不串联两套增益造成误导。

### 5.2 区域统计与时间稳定

只读核对桌面版源码可见其 32×18 场景取样、单点归约、低分辨率照度纹理和 3×3 空间降噪；没有可据此直接认定的手机端运行结果。[D1] 移植时保留思路，不直接认定原 shader 在移动 GPU 上数值与性能等价。

手机端统计网格采用最长边 64、另一边按区域比例计算并限制在 16–64 个采样点；由分层 GPU 归约得到加权对数均值、亮区占比与有效样本权重。照度图最长边不超过 256，使用边缘感知的插值避免跨过强边界过度增亮。

特别处理对数亮度：负对数值不能直接写入会夹紧到 0–1 的普通纹理而丢失。浮点渲染目标可用时使用受验证的浮点格式，否则采用可逆的规范化编码；两种路径以 CPU 数值参考和 GPU 输出交叉验证。对 NaN、Inf、无样本以及全黑设置明确有限输出。

曝光按时间而非“固定每帧系数”平滑，默认时间常数 0.4 秒；同一静态场景中自动曝光变化限速 1 EV／秒。突变检测使用统计分布与时间连续性共同判断；换镜头时重置并在 0.15 秒过渡。它是参数平滑，不是图像多帧降噪，不宣传为运动补偿。

“锁定当前增强参数”锁定曝光与手动设置；改变选区、媒体或颜色路径后解除锁定并提示。性能降级仍可降低降噪计算量，不能偷偷改变锁定曝光。原画对比暂时旁路像素增强，保持原播放状态、位置、选区与倍数。

### 5.3 高光、噪声与细节

先抑制暗部噪声，再提升可见度；限制强边界两侧的混合，防止把字幕边缘、栅栏、头发与细线抹掉。提亮使用高光压缩的单调映射，并统一约束 RGB 增益，避免单通道硬裁剪造成明显偏色。

细节增强排在降噪之后，默认轻量且具有噪声门控，不用锐化掩饰失焦或运动模糊。真实微光素材应分别报告暗部可见度、残余噪声、边缘光晕与颜色偏移；单独增加平均亮度不等于画质通过。

### 5.4 HDR 与不支持情况

检测 PQ／HLG、HDR 元数据与实际渲染路径。首版完整增强验收限定 SDR；HDR 默认旁路本应用 SDR 增强并显示原因。正常播放与内核显示映射另行验证，不保证所有设备保留 HDR 位深。界面不能在旁路后仍显示“弱光增强已生效”。mpv 对部分 MediaCodec 色彩及位深行为列有注意事项。[7]

## 6. 触控界面与手势状态机

### 6.1 布局

竖屏：上方视频、下方进度和控制区；增强／剪辑面板从底部展开。横屏：紧凑顶部工具栏，底部时间轴与播放控制；不用一整排小字塞满屏幕。按钮触控面积目标至少 48 dp，文字使用系统字体，不捆绑未获许可字体文件。

底部始终有明确的播放／暂停、−10 秒、+30 秒、音量、速度入口。字幕与音轨在“更多”中。普通播放时控制栏 3 秒无操作后可隐藏；暂停、选择、剪辑、面板展开及错误提示时保持显示。轻点画面显示／隐藏控制栏，双击左右区快退／快进；系统返回优先关闭面板或取消选择，而非直接退出。

### 6.2 手势归属

优先级固定为：**对话框与面板 → 已抓取的滑块／手柄 → 框选模式 → 放大视图缩放／平移 → 普通播放手势。** 一个触摸序列只有一个拥有者，不能在移动中同时被多个控制器解释。

状态包括普通浏览、进度拖动、A 拖动、B 拖动、选区待画、选区绘制、选框调整、双指缩放、放大平移和触控锁定。按钮抬手事件不得再作为新选框的落点。跟踪 `pointerId`，出现 `ACTION_CANCEL`、应用失焦、Surface 重建或不支持的多指组合时安全取消本次序列。

框选操作：点击“区域放大”仅进入模式并保存原状态；一指拖出矩形；支持四角调整与整体移动；点击“应用”提交后恢复进入前的播放状态。过小选区保留待选状态，不退出、不触发其他手势。点击“取消”恢复原视图；“全画面”清除手工区域。最小有效源区域为 16×16 像素，初次绘制屏幕边长须均达到 24 dp；小目标可先整体缩放再选择，但不能宣称放大产生新细节。

放大后双指缩放 1–8 倍，一指平移。此时一指平移不再用于快进或左右亮度／音量手势，音量通过可见控件操作。触控锁定时仅保留明显解锁入口，不因误触旋转、改变区间或退出。

### 6.3 时间轴行为

播放进度拖动时记住原暂停状态，预览请求最多每 150 ms 一次，只保留最新请求；松手发出最终定位，待完成后恢复原状态。视频尚无时长或不可寻址时禁用拖动并显示说明，不用 0 秒假充已定位。

A／B 手柄相互不跨越，视觉热区错位，短片段也可分别抓取。长视频提供时间轴局部放大和时间输入，输入合法条件为 `0 ≤ A < B ≤ duration`；内部以整数微秒保存，不用屏幕像素直接作为时间数据。边界预览停在可解码帧，界面区别请求时间与实际帧时间，尤其不能按固定帧率假算 VFR。

## 7. 两条导出路径

### 7.1 原码流剪辑

使用同一固定 FFmpeg 基线的原生库和独立 JNI 导出桥接，只封装复制，不在手机上调用桌面 `ffmpeg.exe`，也不将未知下载的命令行程序作为依赖。

分析用户选中的视频轨，定位可独立解码的随机访问点。默认实际起点向前对齐；确认框必须同时显示请求 A、实际 A′、请求 B、预计时长与额外包含的前段。遇到开放 GOP、损坏索引或无法确认起始可解码性时，不仅凭“key_frame”标签保证安全；提示选择精确模式，或经用户确认改用可证明有效的边界。

首选同容器、同视频压缩格式输出；MP4 不兼容的轨道组合可建议 MKV。对选中音轨与字幕逐一列明保留／不支持项，不静默丢弃。附件、封面、章节等不属于保证全量保留范围，确认窗口显示具体处理结果。

音视频使用同一个时间基准平移，保留重排序关系；不分别归零破坏原始音画偏移。末尾还受包与依赖边界约束，因此实际区间写入导出结果摘要。可变码率片段的平均码率不必等于全片，不以平均码率相同作为无损判断。

同容器样本复制测试要求所有已复制视频包负载与源包一一匹配。必须变换封装表示时，分别验证压缩码流内容与封装转换，报告不能继续套用“原始字节逐包完全一致”。

### 7.2 精确剪辑

通过 Media3 Transformer 输出 MP4／H.264 与 AAC，读取源文件而非屏幕录制。优先可用硬件编解码器；源格式或设备能力不满足时，明确拒绝该导出模式，不把未经测试的软件后备编码默认为可用。

采用真实边界裁剪，关闭仅靠编辑列表隐藏前段的快速裁剪方式。官方文档提醒编辑列表预滚可能保留用户以为被移除的内容。[9] 必要的重编码不能称为原码流；导出结果须记录实际编码器和每轨复制／重编码状态，不仅记录请求的 MIME 类型。

输出优先保持源尺寸，设备不支持时，在确认框提出降分辨率选择；不能静默缩小。码率设置显示为目标值而非原码率保证。首版精确导出限定 SDR 和选中的一个视频轨／一个音频轨，字幕不烧录，未保留项必须显示。无音轨输入允许导出纯视频。

选择“原码流”或“精确”均不写入播放增强、选区或用户附加旋转。源文件自身的方向元数据则应保持视觉方向正确：保留或按输出链路正规化，不与用户的临时旋转混淆。

### 7.3 文件提交与取消

先写应用私有暂存文件，完成容器收尾并校验后，再向用户通过系统选择器创建的**新文件**复制；不覆盖原输入或现存输出。URI／文档 ID 可比时做身份检查，但不能以字符串不同就证明不是同一文件。

SAF 提供方不保证所有路径都有原子重命名能力。向外部文档复制时保留提交中状态；失败或取消则尝试删除本任务创建的半成品，删除失败明确展示残留位置。原文件始终只读。未知大小、磁盘不足、授权被撤销、断开存储、超时和取消分别有可读错误消息。

## 8. 文件访问、权限与生命周期

默认使用系统文件选择器／文件夹授权，不申请“所有文件访问”、摄像头、麦克风、无障碍或悬浮窗权限。只持久化系统实际授予的 URI 权限；移动或删除文件后授权可能不再有效，需要重新选择。[10]

可寻址 `content://` 输入直接通过受控 FD 或原生读取桥接访问，不强行猜测真实路径。不可寻址源需要缓存时，先说明原因并征得同意；缓存上限取可用空间减 256 MiB 保留量，长度未知时边写边检查并允许取消。不得为每次打开本地视频默认复制整个大文件。

只加载应用内置的配置与着色器，不自动执行视频目录中的 Lua 或其他脚本；不允许外部 Intent 注入任意内核命令。首版本地模式不提供网络地址打开、不内置遥测或账户 SDK；不依赖 Google 服务登录。系统 DocumentsProvider 自身可能提供远程文件，此时提示来源与可用性，不声称外部提供方也离线。

最近播放信息和断点只保存在应用私有目录，并提供清除入口。截图为当前渲染视频像素，默认不含控制按钮；增强、区域裁剪和字幕是否包含在截图中须在保存提示中列明。不能用系统背光变化作截图增强证据。

前后台切换默认暂停；可用的后台音频／画中画需要单独启用并遵守系统生命周期。精确转码为用户发起任务，进入后台时采用系统支持的可见任务承载方式；首个测试版若未完成相关适配，退到后台应安全取消并提示，不声称永不被系统中断。长按电源、来电、系统内存回收或用户强行停止均不能被应用保证阻止。

## 9. 流畅度与资源保护

### 9.1 默认策略

默认自动均衡。增强工作纹理最长边先限制为 1920，保持比例并从源纹理取样；源解码纹理不因此缩小。选区放大优先使用原区域的真实像素，额外的高分辨率细节档只能在通过性能测试后开放。不得经全屏截图或先把视频缩为小预览再放大选区。

额外 GPU 资源设计预算为最多两个 1920×1080 RGBA8 工作纹理、低分辨率统计／照度资源与 1×1 参数历史，估算上限约 32 MiB；浮点颜色路径可提高至 64 MiB。以上仅为增强模块预算，不包含解码器、窗口缓冲、libmpv 缓存和系统驱动资源，不能用作总内存保证。增强统计状态不保存整段视频。

正常播放不逐帧回读完整图像到 CPU。验收截图是显式测试操作；运行诊断仅允许低频小统计量异步回读，且不得让 UI 等待 GPU。

### 9.2 降级规则

以连续 5 秒有效播放窗口统计掉帧／呈现异常，排除启动前 5 秒、主动定位后 2 秒、暂停、缓冲及应用失焦期间。若连续两个有效窗口的掉帧比例超过 1%，先关闭细节增强，再降低空间降噪，之后改用流畅优先；仍不满足再旁路像素增强。每次改变间隔至少 10 秒，30 秒稳定后才允许尝试恢复一级，避免反复跳档。

API 提供热状态时纳入调度；读取不到则显示“热状态不可用”，不填 0 冒充正常。Android 热状态接口有版本条件，使用前必须检查。[11] 降级保留选区、手势、时间轴与音量，明确显示“请求档位／实际档位／原因”。锁定参数不取消过热保护。

### 9.3 真机验收目标

Mate 20 X／HarmonyOS 4.0 的优先目标为本地 1080p30 SDR，连续 20 分钟，自动均衡和一个中等选区放大分别测试。排除前述过渡区间后，目标呈现掉帧比例不高于 1%，无持续超过 0.5 秒的非缓冲停顿，无 ANR；记录原画、增强、区域增强三组结果。1080p60、4K30 与4K60另列能力等级，不能外推为全部支持。

能使用有效 GPU 计时时，再报告新增增强阶段的 P50／P95 耗时，1080p30 以 P95 不超过 8 ms 为调校目标；无可靠计时则标记未测，不能用 UI 刷新次数代替视频帧率。运行 20 分钟的末段必须单独统计，以观察发热后降频表现。未达标就标记该设备／档位不满足验收，不更改口径掩盖失败。
